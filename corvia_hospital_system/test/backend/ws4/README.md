# WS4 isolated PostgreSQL contract tests

This is a **known-vulnerable baseline**, not a security fix or a migration.
Tests marked `KNOWN_BASELINE_GAP` succeed when they reproduce a recorded defect.
A green run does not mean Corvia is secure, deployed or integration-ready.

## Run on Windows

Prerequisites: Python 3.10+ and existing PostgreSQL **15.x** binaries (including
`initdb`, `pg_ctl`, `postgres`, `psql`, their DLLs, `share`, `plpgsql` and `dict_snowball`). A
portable Windows archive is linked from the official PostgreSQL download page.
No Python packages, Docker, Windows service or global installation are required.

From the repository root, using your installed Python and PostgreSQL paths:

```powershell
python test/backend/ws4/run_tests.py --pg-bin 'C:\path\to\pgsql\bin'
```

The runner accepts **no database URL**. It creates a fresh random directory under
`build/ws4-db/`, initializes a new cluster with a random password, binds only to
`127.0.0.1` on an available port, runs synthetic tests, and stops that exact
cluster in `finally`. It never resets an existing database or changes the shared
Corvia backend. Passwords are not printed; the temporary initialization password
file is removed after initialization. Synthetic cluster files and logs remain
under the ignored build directory for diagnosis; they are not a live-data backup.
If the process is forcibly terminated, inspect its `result.json`/`postmaster.pid`
and stop only that recorded test cluster with `pg_ctl -D <its-data-path> stop`.

The result file records the actual PostgreSQL version, local port, test outcomes,
SQL errors, baseline hash and whether the server stopped. An available port can
be claimed by another process before startup; the runner fails rather than
connecting to an existing server if its own cluster cannot start.

## What is reconstructed

`baseline/catalog.sql` contains the selected profiles/incidents columns, their
exported constraints/indexes/triggers, all incident policies, profile write and
own-profile read policies, relevant function bodies/owners
and explicit API grants from the supplied 5 October 2026 PostgreSQL 15.8 catalog.
Seven relevant functions retain their exported definitions, including the legacy
claim RPC. This is separate from `supabase/migrations/`: **never apply this file
to Testing/live**. It deliberately includes unsafe grants/policies to reproduce
the findings. It is not generated by replaying historical batch SQL, which can
overwrite later role constraints.

`baseline/provenance.json` maps definitions to one-based source records and pins
the supplied CSV SHA-256. The CSV itself is not copied into the repository.
To verify deterministic reconstruction when that original export is available:

```powershell
python test/backend/ws4/build_baseline.py --catalog 'C:\path\to\metadata.csv' --check
```

Omit `--check` only when deliberately rebuilding the selected baseline. A new
export hash is rejected until reviewed; do not merely update the expected hash
to accept drift. The generated SQL is committed as a test fixture so teammates
can run tests without sharing the original export.

## Explicit substitutions and limits

- `auth.users` contains synthetic IDs only. `auth.uid()` reads a session claim
  setting. Sessions use `SET ROLE authenticated/anon`; PostgreSQL grants/RLS and
  function ownership are real, but token verification, Auth bans and HTTP API
  reachability are not tested.
- `lab_worker_accounts` is a minimal dependency stub so the exported profile
  trigger exists unchanged. Tests exercise non-lab paths; this is not a lab
  compatibility suite. Other database objects/default privileges are not restored.
- Three additional permissive profile SELECT policies for doctor, hospital-admin
  and pharmacist access are omitted, listed in provenance. They require unrelated
  hospital/dispensing tables. No profile write policy is omitted; own-profile
  visibility needed by these tests remains exact. Cross-module profile reading
  is not verified by this harness.
- Two proposed organization labels exist only in `ws4_fixture.coverage`. The
  existing policy ignores them. This demonstrates absent scope enforcement,
  not a deployed organization schema or an agreed WS5 contract.
- New-profile upsert tests model the relevant profile part of registration,
  not email verification, storage, staff linking or the full signup journey.
- This PostgreSQL server is not a local Supabase stack. It cannot serve the
  Flutter application, Auth, PostgREST or Realtime.

## Coverage and next gate

Compatibility cases cover patient isolation, anonymous and inactive denial,
legacy claim fields/errors, same-owner retry, supervisor access, ownership guards,
ordinary profile edits, profile upsert and conditional patient cancellation.
Concurrent cases use separate database sessions and inspect `pg_stat_activity`
to confirm a real lock wait before releasing the first transaction. They verify
one claim winner, cancellation-before-claim and claim-before-conditional-cancel
behaviour. A failed transaction also verifies that claim ownership/state roll back.

Known-gap cases reproduce profile self-promotion/reactivation, null activation,
unrestricted own-incident status changes, missing organization scope and initial
profile privilege assignment. Treat their successful reproduction as evidence
for correction, never as acceptance of the unsafe behaviour.

Before a deployable correction, agree the canonical organization/membership
contract with backend/WS5, inspect WS5/WS6 code when available, and add a separate
corrected-contract suite proving these unsafe operations are denied without
breaking legitimate clients. No production membership model or corrective
migration is supplied by this baseline checkpoint.
